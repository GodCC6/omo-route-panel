*Historical Evidence Note: This document records the 2026-10-26 root-cause analysis and verification for LaunchAgent persistence, runtime upgrade adaptation, and Tailscale session token renewal (baseline commit `50cb8b1`). It is retained as historical operational evidence.*

## Root Causes Identified (2026-10-26)

1. **Ephemeral terminal lifecycle**: The panel server had been started inside an interactive agent terminal session. When the host terminal exited, port `4177` stopped listening while Tailscale Serve on port `9443` stayed up and returned HTTP `502`, causing both SSE notifications and catalog refresh requests to fail.
2. **Hardcoded runtime version and digest allowlist**: The initial native adapter pinned a single OMO version and static digest table. When the local OMO installation upgraded from `5.1.46` to `5.1.48`, the adapter rejected it with `engine-launcher-mismatch`, causing 10 of the 66 baseline tests to fail.
3. **In-memory token rotation across restarts**: Restarting the server rotates its in-memory bearer token. Previously, an already-open remote browser tab did not re-bootstrap via Tailscale identity on HTTP `401`, leaving the tab stuck on `401` after the backend recovered.

## Fixes Implemented

- **User LaunchAgent (`com.omo-route-panel.web`)**: Managed via `scripts/service.mjs` with `RunAtLoad` and `KeepAlive`, decoupling the server from interactive terminal sessions while continuing to bind solely to `127.0.0.1:4177`.
- **Dynamic launcher-to-runtime discovery**: Discovers the active runtime corresponding to the launcher binary without a static OMO/SDK version or digest allowlist, while preserving export/shape validation, live binary digest binding, mid-read consistency checks, and real-versus-mirror equivalence.
- **Decoupled SDK catalog worker**: Catalog queries run through the zero-session SDK worker independently of the native report version gate.
- **Single-retry Tailscale session renewal**: On HTTP `401` in Tailscale HTTPS mode, the browser re-bootstraps its in-memory token once via `/api/session` (coalescing concurrent requests) and reconnects the SSE stream while preserving unsaved drafts. HTTP `403` responses are not retried.

## Verification Evidence (2026-10-26)

- Type checking, linting, build, and **69/69 tests passed**, covering future compatible runtime versions, live launcher symlink switching, malformed report rejection, zero-inference SDK catalog queries, and LaunchAgent plist escaping.
- Live HTTPS endpoint returned HTTP `200` with **547 models, 10 categories, and 7 agents**.
- Read-only catalog verified presence of `minimax-cn/MiniMax-M3.1-Flash` without reading or echoing personal configuration text.
- In an isolated browser session, clicking "Refresh catalog" returned `200`. After forcefully terminating the server process once, `launchd` automatically respawned it (`PPID=1`, `TTY=??`); the open page observed `502 -> 401 -> /api/session 200 -> /api/events 200` with a single page navigation count, and subsequent catalog refreshes succeeded with no token in the URL, `localStorage`, or `sessionStorage`.
- Synthetic SSE invalidation and zero-inference checks passed without restarting unrelated services.
